# Lacy user manual

Lacy helps people find their way around an unfamiliar codebase. An expert records
what matters in a project, an LLM turns it into a **code tour** — a sequence of
steps, each tied to real lines in real files — and learners walk through it inside
VS Code, with quizzes, questions back to the expert, an optional podcast, and a
dashboard showing how everyone is getting on.

This manual covers using Lacy. For installing and running the server, see the
[README](../README.md).

## 1. Who does what

**Experts** know the project. They write guided tours, answer questions and see the
dashboard.

**Learners** are new to the project. They take the tours assigned to them, ask
questions on any step, and take the quiz.

Anyone can generate an **exploratory tour** for themselves, expert or learner.

Accounts are created by whoever runs the server; there is no sign-up page. Ask them
for an email and password, or see "Managing accounts" in the README if that is you.

## 2. Signing in

1. Open the project you want a tour of in VS Code (**File ▸ Open Folder**). Lacy
   works on the folder that is open, so this matters.
2. Click the **Lacy icon** in the activity bar on the left.
3. Fill in the three fields:
   - **Lacy server** — the address your team's server runs on, e.g.
     `http://lacy.your-team.com:4000`. Whoever set it up will tell you. It is
     remembered, so you only type it once.
   - **Email** and **password** — the account you were given.

If the address is wrong or the server is down, Lacy says it cannot reach a server
there, rather than pretending your password was wrong. You can change the address
later from the command palette: **Lacy: Set Server URL**.

You stay signed in for 30 days, or until you click **Logout**.

## 3. Taking a tour

The **My Tours** tab lists the guided tours assigned to you for the open project.
Click one and press **Start**.

For each step, Lacy opens the file, highlights the lines the step is about, and
shows the explanation in the sidebar. Move with **Next** and **Back**, leave with
**×** — your progress and time spent are recorded either way.

On the last step, **Complete** takes you to the quiz, if the tour has one, and then
to a short feedback form (a 1-5 rating and an optional comment). The rating is what
the expert sees on the dashboard, so it is worth being honest.

If a step shows a note like *"This step's code has moved"* or *"has been edited since
the tour was written"*, see [section 12](#12-how-tours-stay-attached-to-the-code).

## 4. Quizzes

A tour may end with a quiz written by the expert (often generated alongside the tour
and then edited).

- **One attempt per tour.** Once you submit, your score is recorded and you cannot
  retake it.
- Questions are single-answer, multiple-answer, or free text.
- Multiple-answer questions are all-or-nothing: every correct option and no
  incorrect ones.
- After submitting you see your score and which answers were right.

Returning to a tour you have already been quizzed on shows your previous answers
rather than a fresh quiz.

## 5. Asking questions

While on a step, use **Ask a question** to ask about that specific step. The question
is recorded against the step and the tour, and appears on the expert's dashboard,
where they can answer it.

Answers come back the next time you open that step. You can ask several questions on
the same step.

## 6. Writing a guided tour

In **My Tours**, click **New Guided Tour**, then **Autogenerated**:

1. **Name** the tour.
2. **Select files** — up to five. Fewer, well-chosen files give better tours than
   five sprawling ones.
3. Optionally select **line ranges** within a file, to point the generator at the
   part that matters.
4. **Tour focus** — what the tour is for, in a sentence: "how a request reaches the
   database", "what to read before your first bug fix".
5. **AI model** — "Server default" unless your server has more than one configured.
6. **Language** — English or Turkish.
7. **Target department** — which group of learners gets it. The list comes from the
   accounts on your server ([section 13](#13-teams-projects-and-branches)).
8. **Project knowledge level** — how much the audience already knows.
9. Optionally turn on **quiz** and **podcast**.

Generation takes a while — minutes for large files. If it fails, Lacy says why and
nothing is saved, so you can simply try again.

When the tour is created it is assigned to every learner in that department. If
nobody is in it yet, Lacy tells you rather than leaving you to wonder.

**Writing a tour by hand:** choose **Manual** instead, and add each step yourself by
picking a file, a line range and writing the explanation.

## 7. Exploring on your own

The **Explore** tab generates a tour for *you*, on demand, from files you pick and a
question you have ("what happens when a tour is created?"). Exploratory tours are
private: nobody else sees them, and they are not assigned to anyone.

They are the fastest way to get oriented in a part of the code nobody has written a
guided tour for yet.

## 8. Voice to tour

The **Audio** tab lets an expert talk through the code instead of typing.

1. Select the files the explanation is about.
2. Press **Record**, and explain the code as you would to a new colleague.
3. Press **Stop**, then **Create tour**.

Lacy transcribes the recording and uses the transcript as the primary guide for
generation, so the tour follows your explanation rather than the model's own reading
of the code.

Lacy first asks VS Code for the microphone. VS Code usually refuses it to the panel
(on macOS it always has so far), so Lacy then records with the **SoX** command and
the status line says so. Install SoX once (`brew install sox`, `choco install sox`,
`apt install sox`) and restart VS Code fully so it finds the command.

If SoX is missing, Lacy says so as soon as you press record. If a recording captures
nothing, usually because macOS has not given VS Code the microphone (System Settings
→ Privacy & Security → Microphone), it stops and says that, instead of sending an
empty recording. Transcription needs the server's ElevenLabs key.

## 9. Editing a tour

Open a tour you created and choose **Edit**:

- **Rewrite a step's text** — click the step, edit, **Save**.
- **Change which lines a step covers** — select the new range in the editor.
- **Reorder steps** — drag them.
- **Add a step** — **Add new step**, pick a file and range.
- **Delete a step** — the remaining steps renumber themselves.
- **Rename the tour** — click the title.
- **Edit the quiz** — add and remove questions, options and answers.

Editing a step's line range updates what the step is attached to, so the step keeps
pointing at the code you chose even after the file changes later.

## 10. Podcasts

A tour can have a podcast: a generated conversation between an expert and a junior
developer about the code, voiced with ElevenLabs.

Tours that have one show a headphones button. The player shows the conversation as
chat bubbles, the expert on the left and the learner on the right, and marks the line
that is playing. Click any line to play from there, or use previous, pause and next.

The tour's first file opens with its steps highlighted. When a line names one of the
tour's files, that file comes forward with its steps highlighted, and the line gets a
link to it. Leaving the podcast clears the highlights.

Podcasts need `ELEVENLABS_API_KEY` on the server. Without it, the **Create Podcast**
switch is shown but disabled, with a note saying why. If a podcast's audio could not
be made, the tour is still created, and the player says the audio is missing.

## 11. The dashboard

**Experts only.** Click **See Dashboard** under My Tours; it opens in your browser,
already signed in.

- **Codebase Learners** — everyone taking tours: how many they have completed, time
  spent, average quiz score. Click a learner for their detail.
- **Tour Statistics** — tours per project, tours per expert, completion, and the full
  list of guided tours.
- **My Tours** — the tours you wrote, with average rating, completion rate and
  feedback count.
- **Tour detail** — completion, ratings, quiz scores, per-learner progress, every
  question asked (where you answer them), and **which steps no longer match the
  code**.

The dashboard link is valid for five minutes and can only be used once; open it from
VS Code again whenever you need it.

## 12. How tours stay attached to the code

A step points at specific lines, and code moves. Lacy remembers the text of the lines
a step was written against, and when someone opens the step it finds that code again
by content rather than trusting the line numbers:

| What happened to the code | What you see |
|---|---|
| Nothing | The step highlights its lines as written |
| It moved (edits above it, or another branch) | Lacy follows it and notes that it moved |
| It was edited | Lacy still finds it, and notes the description may not match exactly |
| It is gone | Lacy says so, instead of highlighting unrelated lines |

Reformatting and re-indentation do not count as changes.

**For experts:** what readers find is reported back. A tour's page on the dashboard
lists the steps whose code has changed or disappeared, so you know which explanations
need rewriting. The flag clears itself once the step matches the code again.

## 13. Teams, projects and branches

**Departments are teams.** A department is whatever label you choose — `Backend`,
`Platform`, `payments-squad`. Guided tours are assigned to every *learner* whose
department matches. The picker lists the departments your accounts actually use, and
matching ignores capitalisation.

**Tours belong to a repository.** Lacy identifies a project by its git remote, so it
does not matter whether you cloned it as `widgets` and a colleague cloned it as
`widgets-fork` — you see the same tours. A project with no git remote falls back to
the folder name, so everyone needs to use the same folder name for those.

**Branches do not split tours.** You see the same tours on every branch; what changes
is whether each step still matches the code in front of you, which is handled as
described in [section 12](#12-how-tours-stay-attached-to-the-code).

## 14. When something goes wrong

**"Cannot connect" / nothing loads.** The server is not running or `lacy.serverUrl`
is wrong. Check `http://<your-server>:4000/api/health` in a browser.

**Signing in fails.** Passwords are case-sensitive; an admin can reset yours with
`npm run users -- reset-password`.

**A tour I created is assigned to nobody.** Nobody has that department yet, or they
are experts — only learners are assigned tours.

**"See Dashboard" does nothing.** The dashboard has to be built on the server
(`cd dashboard && npm run build`), and only expert accounts may open it.

**Tour generation fails.** Usually a missing or rejected LLM API key on the server,
or files too large for the model's limit. The message says which.

**Recording does nothing, or "No audio received".** VS Code refused the microphone
and SoX is not installed, or macOS has not given VS Code the microphone. Install
SoX, allow VS Code under System Settings → Privacy & Security → Microphone, quit VS
Code fully and try again.

**Podcasts or transcription fail with an ElevenLabs error.** Usually the key: it must
be the full key starting with `sk_`, not the key ID, and allow Text to Speech and
Speech to Text. The server log gives ElevenLabs' reason. After changing `.env`,
restart the server.

**A step highlights the wrong code.** Report it to whoever wrote the tour — and check
the dashboard, which may already be flagging that step.
